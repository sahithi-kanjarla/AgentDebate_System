# Decisions

## M1
- **Python version:** PRD specifies 3.12; local machine has 3.13 only. `requires-python = ">=3.12"`, managed with uv. No 3.12-specific features used.
- **Project root:** repo root is the project root (no nested `tribunal/` folder); backend lives in `backend/`.
- **Review mode:** M1 carries the `mode` field and prompt plumbing only; full review mode is M5.
- **Event log:** every SSE event is persisted in order per debate (for M4 replay) and live streams replay-then-follow from that log.
- **DB access:** sync SQLModel/SQLite calls run via `asyncio.to_thread` so the event loop never blocks.
- **min_critique_rounds (default 1, env `MIN_CRITIQUE_ROUNDS`):** a debate never stops before this many critique rounds, even if round 0 is unanimous (guards against groupthink). Capped by `rounds`; 0 restores PRD-style early stop after round 0.
- **Event log table:** added `debate_event(debate_id, seq, type, data)` beyond the PRD's `Debate`/`Turn`/`CacheEntry`. SSE ids are `seq`; `Last-Event-ID` resumes after that event. Events are persisted before being published to followers.
- **Replay-then-follow:** a running debate has an in-memory `DebateChannel`; late subscribers read from position 0 and then wait for live events. Finished debates stream from the DB.
- **Startup sweep:** debates still `running` at boot are marked `interrupted`.
- **Client note for M3:** the server closes the stream after `done`; `EventSource` would auto-reconnect, so the client must close on `done`. The spec's `error` event name also collides with `EventSource.onerror` semantics; handle via `addEventListener('error')` and check `event.data`.

## M2
- **`openai` SDK (approved):** one `AsyncOpenAI` client per model leg, `max_retries=0` because we own retries so every attempt is counted and logged. Tests inject an `httpx.AsyncClient(transport=MockTransport)`; no `respx`/`pytest-socket` added (a small autouse fixture blocks non-loopback sockets instead).
- **Lineup (agents.yaml):** Gemini `gemini-3.5-flash-lite` (debater_1, per user: Flash-Lite for a higher daily quota), Groq `openai/gpt-oss-120b` (debater_2), OpenRouter `nvidia/nemotron-3-super-120b-a12b:free` (debater_3; pinned rather than `openrouter/free` so runs are repeatable and cacheable), judge Groq `openai/gpt-oss-20b` (Groq limits are per model, so the judge does not share debater_2's quota; originally `llama-3.3-70b-versatile`, retired by Groq 2026-08-16, see "M2 follow-up"). Fallbacks end in local Ollama `gemma4:e4b`.
- **Unverified at build time** (official docs did not confirm; `scripts/smoke_providers.py` checks them live): the exact Gemini Flash-Lite model ID, Gemini free-tier numbers, Gemini support for `response_format: json_object`, and whether Groq's published 30 RPM / 1K RPD / 8K TPM for gpt-oss-120b is the free plan. Gemini's `json_object` is therefore auto-disabled on a 400 mentioning `response_format`; the parser's repair step is the backstop.
- **Retries:** exponential backoff with full jitter on 429/5xx/timeouts/connection errors, 3 attempts per leg. `Retry-After` (or OpenRouter's `X-RateLimit-Reset`) is honored, but a wait over 30s is treated as a spent quota: stop retrying and fall back immediately. 400/401/403/404/402 are not retried but do trigger fallback (bad key, retired model ID).
- **Safe errors:** `str(ProviderError)` is only a category plus HTTP status (e.g. `rate_limited (HTTP 429)`); provider response text stays in `.detail` and is never logged or streamed.
- **Fallback recording:** `Turn.provider`/`Turn.model` hold who actually answered and `Turn.fallback_used` is set. The SSE `agent_response` payload carries only `fallback_used: true`, no provider names, so the debate stays anonymous. A leg with a missing API key is skipped and counts as a fallback.
- **Cache:** on by default (`CACHE_ENABLED`). `CacheEntry` has extra `tokens_in/tokens_out/provider/model` columns beyond the PRD's three so cached calls still report real token stats. Key = sha256 of provider, model, temperature, max_tokens, messages, json_mode. Only successes are cached; the cache sits below the fallback layer, so each leg caches independently.
- **Bug found by the e2e cache test:** the judge transcript listed debaters in completion order, so its prompt (and cache key) changed run to run. It now uses fixed debater order; regression test added. Matters for eval resume in M6.
- **Stats:** `done.stats` gained `api_calls` (HTTP requests sent, retries and failed fallback legs included, cache hits excluded), `cache_hits`, `fallbacks`. Not counted: requests spent when every leg of a call fails.
- **Config split:** `config/agents.yaml` is real; `config/agents.mock.yaml` is the M1 offline demo (`AGENTS_CONFIG=config/agents.mock.yaml`). Tests use the mock config or a fake transport and never the network.
- **Settings:** keys are `SecretStr`; `.env` is looked up at the repo root and in `backend/` (the latter wins). Blank values mean "unset". Logs go through a scrubber that redacts configured key values and `Bearer ...` tokens; prompts and responses are never logged.
- **Reachability:** `/api/agents` probes `GET {base_url}/models` (3s timeout, 45s cache, no generation quota): `ok | no_api_key | unauthorized | model_not_found | rate_limited | unreachable`, per agent and per fallback.
- **Known gaps / risks:** no RPM/TPM limiter (Groq gpt-oss-120b's 8K TPM is the likely first wall; mitigated by `max_tokens: 1536` and backoff); an Ollama cold start took ~30s in the smoke run (timeout is 180s); several agents falling back to Ollama at once queue behind its concurrency of 1.

## M2 follow-up: retired Groq model and the gpt-oss 400
- **Retired model:** Groq retired `llama-3.3-70b-versatile` (2026-08-16). Replaced with `openai/gpt-oss-20b` as the judge and in debater_3's fallback chain (openrouter -> groq gpt-oss-20b -> ollama). `llama-3.1-8b-instant` was never configured; a test now guards that neither retired ID reappears in `agents.yaml`. Trade-off: debater_2 (gpt-oss-120b), the judge and debater_3's fallback are now all one model family, so diversity drops when OpenRouter is down; Gemini and OpenRouter keep two other families in the normal path.
- **Likely cause of `gpt-oss-120b` -> `bad_request (HTTP 400)` (inferred, not yet confirmed against Groq):** the smoke script capped output at `max_tokens=64`. gpt-oss is a reasoning model whose reasoning tokens count against the output limit (default effort `medium`), so the budget ran out before any JSON was emitted, and Groq's JSON mode answers an unfinishable generation with HTTP 400 `json_validate_failed` ("Failed to generate JSON"). Real debates use `max_tokens: 1536`, but the smoke script did not build its request the way debates do, and the provider only recognised a 400 that mentions `response_format`. Groq's docs do not document this error; sources were the Groq docs (reasoning, API reference), which say reasoning needs larger limits than the 1024 default, plus community reports of empty or truncated gpt-oss output with `finish_reason: length`. `scripts/smoke_providers.py --verbose-errors` will show the real message and type.
- **Fixes:**
  - Groq's output-limit field is now `max_completion_tokens` (`max_tokens` is deprecated there); configured per provider as `token_param`, default `max_tokens` elsewhere.
  - New per-model `model_options.extra_body` in `agents.yaml`; Groq gpt-oss models send `reasoning_effort: low` so reasoning cannot consume the whole budget and TPM use stays down. This trades some reasoning depth for reliability and is the first knob to revisit (`medium`) if the eval shows accuracy suffering. Options are part of the cache key.
  - A 400 `json_validate_failed` (code or "Failed to generate JSON" message) now retries that one call without `response_format`, and keeps JSON mode on for later calls. A 400 that rejects `response_format` itself still disables JSON mode for the provider.
  - An empty reply now reports `empty_response (finish_reason=length)` so a spent token budget is visible.
- **Error-body handling bug fixed:** the SDK's `exc.message` is the whole `Error code: 400 - {body}` string, which can include `failed_generation` (model output). `ProviderError.detail` now holds only the error object's own `message` field; `code` and `error_type` are kept separately.
- **Smoke script now mirrors real debates:** it builds each leg with `ProviderRegistry.build_leg` (same temperature, token field, reasoning options, JSON-mode handling) and parses with the real `parse_with_repair`, with a one-attempt policy and no cache. Added `--verbose-errors` (provider error `message` and `type`, 200 characters max, key-scrubbed; never headers, keys or bodies) and `--list-models <provider>` (IDs only).
- **Still unverified:** that the diagnosis above is the actual cause, and that `reasoning_effort: low` is accepted on both gpt-oss models (Groq's API reference lists low/medium/high for them, and a 400 is returned for unsupported values).
- **Observed locally:** a one-token-ish Ollama smoke call took 30s on the first run and 95s on the second, so Ollama fallback turns can be slow; its 180s timeout leaves limited headroom for long critique prompts.
