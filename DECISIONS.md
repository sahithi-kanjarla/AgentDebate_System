# Decisions

## M1
- **Python version:** PRD specifies 3.12; local machine has 3.13 only. `requires-python = ">=3.12"`, managed with uv. No 3.12-specific features used.
- **Project root:** repo root is the project root (no nested `tribunal/` folder); backend lives in `backend/`.
- **Review mode:** M1 carries the `mode` field and prompt plumbing only; full review mode is M5.
- **Event log:** every SSE event is persisted in order per debate (for M4 replay) and live streams replay-then-follow from that log.
- **DB access:** sync SQLModel/SQLite calls run via `asyncio.to_thread` so the event loop never blocks.
- **min_critique_rounds (default 1, env `MIN_CRITIQUE_ROUNDS`):** a debate never stops before this many critique rounds, even if round 0 is unanimous (guards against groupthink). Capped by `rounds`; 0 restores PRD-style early stop after round 0.
- **Event log table:** added `debate_event(debate_id, seq, type, data)` beyond the PRD's `Debate`/`Turn`/`CacheEntry`. SSE ids are `seq`; `Last-Event-ID` resumes after that event. Events are persisted before being published to followers.
- **Replay-then-follow:** a running debate has an in-memory `DebateChannel`; late subscribers read from position 0 and then wait for live events. Finished debates stream from the DB.
- **Startup sweep:** debates still `running` at boot are marked `interrupted`.
- **Client note for M3:** the server closes the stream after `done`; `EventSource` would auto-reconnect, so the client must close on `done`. The spec's `error` event name also collides with `EventSource.onerror` semantics; handle via `addEventListener('error')` and check `event.data`.

## M2
- **`openai` SDK (approved):** one `AsyncOpenAI` client per model leg, `max_retries=0` because we own retries so every attempt is counted and logged. Tests inject an `httpx.AsyncClient(transport=MockTransport)`; no `respx`/`pytest-socket` added (a small autouse fixture blocks non-loopback sockets instead).
- **Lineup (agents.yaml):** Gemini `gemini-3.5-flash-lite` (debater_1, per user: Flash-Lite for a higher daily quota), Groq `openai/gpt-oss-120b` (debater_2), OpenRouter `nvidia/nemotron-3-super-120b-a12b:free` (debater_3; pinned rather than `openrouter/free` so runs are repeatable and cacheable), judge Groq `openai/gpt-oss-20b` (Groq limits are per model, so the judge does not share debater_2's quota; originally `llama-3.3-70b-versatile`, retired by Groq 2026-08-16, see "M2 follow-up"). Fallbacks end in local Ollama `gemma4:e4b`.
- **Unverified at build time** (official docs did not confirm; `scripts/smoke_providers.py` checks them live): the exact Gemini Flash-Lite model ID, Gemini free-tier numbers, Gemini support for `response_format: json_object`, and whether Groq's published 30 RPM / 1K RPD / 8K TPM for gpt-oss-120b is the free plan. Gemini's `json_object` is therefore auto-disabled on a 400 mentioning `response_format`; the parser's repair step is the backstop.
- **Retries:** exponential backoff with full jitter on 429/5xx/timeouts/connection errors, 3 attempts per leg. `Retry-After` (or OpenRouter's `X-RateLimit-Reset`) is honored, but a wait over 30s is treated as a spent quota: stop retrying and fall back immediately. 400/401/403/404/402 are not retried but do trigger fallback (bad key, retired model ID).
- **Safe errors:** `str(ProviderError)` is only a category plus HTTP status (e.g. `rate_limited (HTTP 429)`); provider response text stays in `.detail` and is never logged or streamed.
- **Fallback recording:** `Turn.provider`/`Turn.model` hold who actually answered and `Turn.fallback_used` is set. The SSE `agent_response` payload carries only `fallback_used: true`, no provider names, so the debate stays anonymous. A leg with a missing API key is skipped and counts as a fallback.
- **Cache:** on by default (`CACHE_ENABLED`). `CacheEntry` has extra `tokens_in/tokens_out/provider/model` columns beyond the PRD's three so cached calls still report real token stats. Key = sha256 of provider, model, temperature, max_tokens, messages, json_mode. Only successes are cached; the cache sits below the fallback layer, so each leg caches independently.
- **Bug found by the e2e cache test:** the judge transcript listed debaters in completion order, so its prompt (and cache key) changed run to run. It now uses fixed debater order; regression test added. Matters for eval resume in M6.
- **Stats:** `done.stats` gained `api_calls` (HTTP requests sent, retries and failed fallback legs included, cache hits excluded), `cache_hits`, `fallbacks`. Not counted: requests spent when every leg of a call fails.
- **Config split:** `config/agents.yaml` is real; `config/agents.mock.yaml` is the M1 offline demo (`AGENTS_CONFIG=config/agents.mock.yaml`). Tests use the mock config or a fake transport and never the network.
- **Settings:** keys are `SecretStr`; `.env` is looked up at the repo root and in `backend/` (the latter wins). Blank values mean "unset". Logs go through a scrubber that redacts configured key values and `Bearer ...` tokens; prompts and responses are never logged.
- **Reachability:** `/api/agents` probes `GET {base_url}/models` (3s timeout, 45s cache, no generation quota): `ok | no_api_key | unauthorized | model_not_found | rate_limited | unreachable`, per agent and per fallback.
- **Known gaps / risks:** no RPM/TPM limiter (Groq gpt-oss-120b's 8K TPM is the likely first wall; mitigated by `max_tokens: 1536` and backoff); an Ollama cold start took ~30s in the smoke run (timeout is 180s); several agents falling back to Ollama at once queue behind its concurrency of 1.

## M2 follow-up: retired Groq model and the gpt-oss 400
- **Retired model:** Groq retired `llama-3.3-70b-versatile` (2026-08-16). Replaced with `openai/gpt-oss-20b` as the judge and in debater_3's fallback chain (openrouter -> groq gpt-oss-20b -> ollama). `llama-3.1-8b-instant` was never configured; a test now guards that neither retired ID reappears in `agents.yaml`. Trade-off: debater_2 (gpt-oss-120b), the judge and debater_3's fallback are now all one model family, so diversity drops when OpenRouter is down; Gemini and OpenRouter keep two other families in the normal path.
- **Likely cause of `gpt-oss-120b` -> `bad_request (HTTP 400)` (inferred, not yet confirmed against Groq):** the smoke script capped output at `max_tokens=64`. gpt-oss is a reasoning model whose reasoning tokens count against the output limit (default effort `medium`), so the budget ran out before any JSON was emitted, and Groq's JSON mode answers an unfinishable generation with HTTP 400 `json_validate_failed` ("Failed to generate JSON"). Real debates use `max_tokens: 1536`, but the smoke script did not build its request the way debates do, and the provider only recognised a 400 that mentions `response_format`. Groq's docs do not document this error; sources were the Groq docs (reasoning, API reference), which say reasoning needs larger limits than the 1024 default, plus community reports of empty or truncated gpt-oss output with `finish_reason: length`. `scripts/smoke_providers.py --verbose-errors` will show the real message and type.
- **Fixes:**
  - Groq's output-limit field is now `max_completion_tokens` (`max_tokens` is deprecated there); configured per provider as `token_param`, default `max_tokens` elsewhere.
  - New per-model `model_options.extra_body` in `agents.yaml`; Groq gpt-oss models send `reasoning_effort: low` so reasoning cannot consume the whole budget and TPM use stays down. This trades some reasoning depth for reliability and is the first knob to revisit (`medium`) if the eval shows accuracy suffering. Options are part of the cache key.
  - A 400 `json_validate_failed` (code or "Failed to generate JSON" message) now retries that one call without `response_format`, and keeps JSON mode on for later calls. A 400 that rejects `response_format` itself still disables JSON mode for the provider.
  - An empty reply now reports `empty_response (finish_reason=length)` so a spent token budget is visible.
- **Error-body handling bug fixed:** the SDK's `exc.message` is the whole `Error code: 400 - {body}` string, which can include `failed_generation` (model output). `ProviderError.detail` now holds only the error object's own `message` field; `code` and `error_type` are kept separately.
- **Smoke script now mirrors real debates:** it builds each leg with `ProviderRegistry.build_leg` (same temperature, token field, reasoning options, JSON-mode handling) and parses with the real `parse_with_repair`, with a one-attempt policy and no cache. Added `--verbose-errors` (provider error `message` and `type`, 200 characters max, key-scrubbed; never headers, keys or bodies) and `--list-models <provider>` (IDs only).
- **Still unverified:** that the diagnosis above is the actual cause, and that `reasoning_effort: low` is accepted on both gpt-oss models (Groq's API reference lists low/medium/high for them, and a 400 is returned for unsupported values).
- **Observed locally:** a one-token-ish Ollama smoke call took 30s on the first run and 95s on the second, so Ollama fallback turns can be slow; its 180s timeout leaves limited headroom for long critique prompts.

The e2e tests were updated for the new chains and counts.

## Real-debate fixes (items 1-2 done; 3-4 pending a rule sign-off)
- **Exact answer comparison (replaces the old casefold/strip/punctuation normalizer).** Found in a real debate: `[1] [1,2] [1,2,3]` and `[1] [1, 2] [1, 2, 3]` clustered together, and for code questions that difference can be the whole answer. `normalize_answer` now returns the text untouched (no trim, no case folding, no dropped periods, no whitespace collapsing). The one exception is a *pure number*, matched by `fullmatch` against: optional currency symbol, optional sign, digits (thousands commas only in correct groups of three), optional decimals. Those compare by value, so `42`, `42.0`, `$42`, `1,042`/`1042` merge.
- **Consequences of "pure number" being strict:** `42.`, ` 42`, `42 apples`, `1e5` and `nan` are text, so `42.` no longer merges with `42` (the old code merged them). `1,2,3` used to collapse to 123 because every comma was deleted; it is now a distinct text answer. `-$5` is not recognised (`$-5` is). Clusters' `normalized_answer` in the UI may now contain leading/trailing whitespace.
- **Known cost of exactness:** semantically equal answers that differ in text ("Paris" vs "Paris, France", "4" vs "four") no longer cluster, so consensus is harder to reach and debates run their full rounds more often. Early stop and the majority fallback verdict both use the exact comparison.
- **Pipeline audit for whitespace:** nothing in parsing (`extract_json`, Pydantic), the schemas (no `str_strip_whitespace`), SQLite JSON columns, the SSE JSON encoding, the response cache or the OpenAI-compatible provider alters `final_answer`; a regression test sends `" X "` and a multi-line, indented, newline-terminated verdict through the HTTP API, the live stream, stored turns and the stored event log. Template rendering strips only the prompt templates, never the question or answers.
- **Prompts:** debater, critique and judge prompts now say `final_answer` is only the answer in the form the question asks for, character-exact for program output (whitespace, indentation, capitalization, punctuation preserved, newlines written as \n), and that "[1, 2]" vs "[1,2]" count as different. They no longer ask for "short, normalized" answers. A test checks no prompt contains a model or provider name.
- **changed_mind is derived by the server.** A turn counts as changed when its answer cluster differs from that agent's last valid answer (`previous_cluster_id` is in the payload; round 0 and agents with no earlier valid answer are never "changed"). A whitespace-only edit counts as a change, a numeric respelling (408 -> 408.0) does not. The event/stored `changed_mind` is the derived value; the model's own boolean is kept as `changed_mind_claimed`, and `changed_mind_because` is still the model's text. The judge transcript now reports "Changed answer from X" only for derived changes, instead of repeating the model's claim.

## Real-debate fixes, items 3 and 4
- **`received_critiques` (on `round_complete` and on each stored turn's `parsed_json`):** the critiques raised in round r against the answer an agent held in round r-1, i.e. "critiques raised against the answer this agent revised". Each entry is `{from_agent, issue, severity, round}`; every debater label gets a key (empty list if unchallenged); round 0 is `{}`. It is filled in when the round closes, because a critique of agent A can arrive after A's own `agent_response` was emitted, so it is deliberately absent from `agent_response` events (stored turns carry it as an extra key; the event log does not). **It is not a claim that those critiques caused a change.** Agents do not currently see critiques addressed to them: a critique prompt contains only peers' final answers, confidence and reasoning, not their `critiques` list. Feeding critiques back to their targets is a possible future experiment for the eval (M6), compared against the current behaviour.
- **`mistakes_caught` is built by the server, not the judge** (`app/debate/mistakes.py`). The judge keeps writing `summary`, `dissent`, `confidence` and `consensus_reached`; the judge prompt no longer asks for `mistakes_caught`, and anything it returns for that field is overwritten. The payload shape is unchanged. Rule: a critique raised in round r by critic C against target T counts when (1) T's answer before round r (its latest valid answer from earlier rounds) differs from the verdict's `final_answer`, and (2) C's own round-r answer equals the verdict's `final_answer`. Equality is the consensus one: exact text, pure numbers by value. It is attributed to C, in round r, with the critique's `issue` as the description. One entry per (target, wrong answer); the first critique wins. Critics or targets without a valid answer, and self-critiques, are skipped. The same rule runs against the majority fallback verdict when the judge is unavailable.
- **Ordering detail:** "first" means round order, then debater order (Debater 1, 2, 3), then the critique's position in that debater's list, not the order events happened to arrive. Arrival order depends on which provider answered first, which would make the list (and the cached judge prompt context) vary run to run.
- **Limitation, a wrong verdict:** the list is only as good as the verdict. If the judge (or the majority) picks a wrong answer, critics who held that answer are credited with catches and critics of the actually-correct answer are not.
- **Limitation, exact comparison:** answers that are textually different but semantically equal (`[1,2]` vs `[1, 2]` where the question does not care about spacing, "Paris" vs "Paris, France") count as different, so a critique of the equivalent answer produces a false catch, and agreement is under-detected.
- **Replay test:** `tests/test_mistakes.py` replays the mutable-default-argument debate: three exact-distinct answers in rounds 0 and 1 (right, wrong spacing, wrong), Debater 1 right throughout and criticising the other two in round 1, the other two critiquing back while wrong (not credited), both switching in round 2 (a late repeat critique is a duplicate and dropped). The list credits Debater 1 twice in round 1 and nobody else, whatever the judge claimed.

## M3: frontend (React, Vite, TypeScript, Tailwind v4)
- **Stack and versions (pinned by the lockfile):** react 19, react-router-dom 7, vite 8, tailwindcss 4 with `@tailwindcss/vite`, vitest 5, jsdom, @testing-library/react and jest-dom, eslint 10 with typescript-eslint, prettier 3. Beyond the approved list I also had to add `@eslint/js` and `globals` (required by ESLint's flat config) and `@types/node` (vite.config.ts and the CSS-parity test). No TanStack Query: three plain GETs use a small `useFetch` hook.
- **Fonts (self-hosted via @fontsource, no Google Fonts requests), all SIL Open Font License 1.1 (checked in each package's LICENSE):** Newsreader (headings, question, ruling), Instrument Sans (UI), JetBrains Mono (answers and code).
- **Tokens:** one file, `src/styles/tokens.css` (Tailwind `@theme`). `src/lib/palette.ts` exports debater, severity and cluster colours and mirrors the CSS; `palette.test.ts` fails if they drift and checks WCAG contrast. That test caught the first teal (4.35:1 on its tint), now `#0a6c67`. Brass is only used as text on vellum/paper (it is 4.2:1 on mist). Cluster hues overlap debater hues by necessity, so clusters are always a chip with a letter and a pattern, and debaters a ring + persona glyph + position.
- **Review mode is disabled** in the UI until M5, with a "Coming in a later milestone" note. `rounds` is not exposed; the backend default applies: `default_rounds = 3` critique rounds after round 0, `min_critique_rounds = 1` (early stop once all agree).
- **Reducer (`src/lib/debateState.ts`):** pure, idempotent, never throws. Dedupes by SSE `seq` (so a reconnect replay is harmless) and otherwise relies on upserts, so out-of-order events converge (`round_complete` before a late `agent_response`, thinking after an answer). `changed_mind` is read from the server field only; `changed_mind_claimed`, `label_map` and anything provider/model-like are dropped, not stored. `final_answer`, cluster answers and the verdict answer are never trimmed.
- **The judge is announced as `agent_thinking {agent: "Judge", round: N+1}`.** Found by running the real stream: the first reducer turned that into a fourth column and a phantom round. It now sets `judging: true` (shown as "The judge is reviewing the debate…") and never creates a turn; the fixture includes the event.
- **Live and finished debates share one reducer and one page, but not one transport (deviation from the plan).** `GET /api/debates/{id}` already returns the stored `events`, so a debate that is not `running` (finished, interrupted, failed, opened from a shared URL) is folded from that single response, while a `running` one is followed over SSE. Reason: an interrupted debate's stream ends without `done`, and `EventSource` would reconnect forever. A test renders the same events both ways and asserts identical HTML.
- **SSE client (per M1 notes):** closes after `done`; the `error` event name collides with `EventSource`'s built-in event, so one listener treats a `MessageEvent` with string data as an application error and anything else as a connection problem. Connection drops let the browser reconnect (the server honours `Last-Event-ID`), giving up after 4 consecutive errors. Keepalive pings are comments and never reach listeners. Events are batched (30 ms) so a replay renders once, not per event.
- **Wording rules honoured:** received critiques are labelled "Critiques of the answer it revised" (round 1 onward only); nothing says a critique caused a change; the changed-mind badge comes from `changed_mind` and shows the previous answer. `changed_mind_because` is not shown in M3; M4's inspector should use `received_critiques`, labelled the same honest way.
- **Critique text uses the critic's own "Response N" labels.** The header shows the resolved pair ("Debater 1 -> Debater 3") and the issue text is rendered verbatim, so the two can disagree. M4 may add a clearly marked substitution.
- **Before deployment (M7) the server must withhold provider/model and `label_map` from the browser until the reveal.** Today `agent_response.payload.label_map` is streamed, and `GET /api/debates/{id}` returns `provider` and `model` on every turn. The UI never renders or stores them (`api.getDebate` drops `turns`; the reducer drops `label_map`; a page test asserts none appear in the DOM), but they are visible in the browser's network tab. Left unchanged in M3 by decision; resolve alongside M5's reveal feature.
- **M7 note, SPA fallback:** Vite serves `index.html` for `/debate/{id}` in development. In production FastAPI must return `index.html` for non-API paths or shared URLs 404.
- **Dev setup:** the Vite proxy sends `/api` to `http://127.0.0.1:8765` (override with `API_TARGET`, used to verify against a second mock backend), so no CORS is needed. Tests use a scriptable `FakeEventSource` (jsdom has none) and a stubbed `fetch`; vitest runs with `css: false`, so the CSS-parity test reads `tokens.css` from disk. Test timeout is 20 s because the first jsdom render is slow on this machine.
- **Smoke-test incident:** an older uvicorn (PID 2800) was already bound to port 8765 on the *real* config (Gemini, Groq, OpenRouter) with code older than the repo (no `changed_mind_claimed`). My first smoke debate went through it by mistake, using a handful of free-tier requests. Afterwards verification ran against a separate mock backend on 8766 with a throwaway database. Restart the 8765 server before using the UI.
- **Not verified:** I had no browser available, so the layout, colours, responsive stacking and reduced-motion behaviour have not been looked at on screen; only DOM structure, accessibility roles and the data flow are covered by tests.

## M4: Debate Graph (VIS1, VIS2, VIS3, legend)
- **One state path, no reducer or backend change.** The graph is `buildGraphModel(state, question)` (`lib/graphModel.ts`, pure, layout-free), laid out by `lib/layout.ts` (d3-scale, fixed pitch, 2 to 7 debaters, any number of rounds) and narrated by `lib/narrate.ts` (templates). `Debate.tsx` passes the same `DebateState` that the Columns view uses; Graph is the default, Columns one click away. "Which edge just arrived" is found by diffing the previous and next model in `useFreshIds`, so the reducer needs no sequence numbers.
- **Critique edge geometry.** A critique raised in round r targets the answer given in round r-1, so its edge runs from the target's round r-1 node to the critic's round r node, with the severity marker at the critic (accuser) end. Chosen so the edge never points at a node that did not exist when the critique was made and the picture never implies a critique caused a change. The legend says so, and the tooltip, aria label and narrator always say who flagged whom. A critique line therefore shares its curve with a faint "reading" edge; parallel critiques between the same two nodes are offset into lanes.
- **Honest copy.** The inspector shows "Critiques of the answer it revised" (from `received_critiques`) and never `changed_mind_because`, so PRD VIS2's "Why did it change its mind?" is deliberately not built (agents do not see critiques addressed to them). The honesty note sits under the graph.
- **Older stored debates.** Missing cluster ids fall back to the round summary, then to one stand-in id per distinct answer; a missing `previous_cluster_id` (no server-derived `changed_mind`) is derived by comparing the agent's answers across rounds and the inspector says "worked out by comparing answers"; missing `received_critiques` fall back to the critique edges of that round. Covered by the `legacy` fixture and tests.
- **Dark stage.** The canvas is a fixed dark panel ("night court") whatever the page theme; tokens `--color-stage-*` plus lighter cluster/severity variants live in `tokens.css`, mirrored in `palette.ts`, parity- and contrast-tested (4.5:1 text, 3:1 marks). Clusters are always colour + letter + fill pattern; severity is colour + width + dash + marker shape (dot, triangle, diamond, as in `SeverityIcon`). The fifth and later answers use a neutral grey, hollow, with their own letter.
- **Performance.** No SVG filters at all: glow is radial gradients and double strokes. The faint reading edges are batched into one path per round (up to 126 edges at 7 x 3 become 3 DOM nodes). Idle breathing and pulses are CSS only; zoom writes its transform straight to the DOM through a ref. framer-motion is used only for the inspector drawer.
- **Motion rules.** Live (`connection !== 'closed'`) animates only what arrives after the first render; a finished or reloaded debate, a reconnect replay's first batch, and `prefers-reduced-motion` all render static (`data-motion="off"`). The real mock backend answers instantly, so through it the graph is effectively always static; use the `?live=1` fixtures to see arrivals.
- **Cluster halos** are drawn per column for 2+ agreeing debaters as a stroked capsule through the members. Rows are fixed per debater, so a different answer sitting between members is cut out of the halo (found in the first screenshot review, where it looked like the odd one out belonged to the group).
- **Legend** is dismissible, remembered in localStorage (wrapped in try/catch), closed on first visit on narrow screens, and always sits under the canvas, never over it.

### Rate limiting (FR10)
- **slowapi is used for its limiter, in-memory storage and moving-window strategy (from `limits`), not its decorator.** The decorator runs before the body is parsed and cannot skip or refund a hit, and a rerun that costs no provider calls must not count. `app/core/ratelimit.py` does the counting; the route decides what is charged. Counts are per process and reset on restart (fine for one container). Tests control time by patching `limits.storage.memory.time` plus the admission clock; nothing sleeps and no `freezegun` was added.
- **Settings (all env-configurable):** `RATE_LIMIT_ENABLED` (default false), `RATE_LIMIT_PER_HOUR=5`, `RATE_LIMIT_PER_DAY=20`, `GLOBAL_DAILY_CAP=15` (0 = off), `MAX_CONCURRENT_DEBATES=0` (off; independent of the enabled flag), `TRUSTED_PROXY=0`. Startup logs one line saying whether rate limiting is ON or OFF (with the numbers), so a deployment cannot silently run unprotected. M7 must turn it on.
- **Global cap = 15, reasoning:** the tightest free quota is OpenRouter at about 50 requests/day (unverified) and each debate sends 2 to 4 calls there (round 0 plus 1 to 3 critique rounds): 50 / 3.3 is about 15. Beyond that the fallbacks carry the load and model diversity drops. It is counted from the database, not memory: debates created since UTC midnight, running ones included, finished ones that sent zero HTTP requests (`stats.api_calls == 0`, i.e. all cache hits) excluded, finished ones with no stats counted. It survives restarts and stores no IPs. Small race: requests in flight at the same instant can overshoot by a few.
- **What costs nothing is not counted.** All reads (GET, streams, showcase) are unlimited. A POST is exempt from the per-IP and global counts when a previous debate is "replayable": same exact question, mode, rounds, seed, min-critique setting and a hash of the agent lineup plus all prompt files (stored in `config_json.fingerprint`), status completed, no `error` events and no fallback, response cache on. Failed calls are never cached, so a debate with errors or fallbacks would send those calls again and is counted. Legacy debates with no fingerprint never match. The check errs toward counting. A refused request is never counted, and exempt requests still obey the concurrency cap.
- **Client IP.** `TRUSTED_PROXY=0`: the socket peer, `X-Forwarded-For` ignored (any client can send it). `N>0`: the Nth entry from the right, validated as an IP; entries a client prepends sit on the left and are never read; a missing, short or malformed header falls back to the peer. I expect `N=1` on Hugging Face Spaces but have not verified how many proxies it adds: check the observed address after deploying (M7).
- **429 body:** `{error: "rate_limited", scope: "ip_hour"|"ip_day"|"global_day"|"busy", message, retry_after_s}` plus `Retry-After`. `global_day` waits until UTC midnight; `busy` is always 30 s. Order of checks: per-IP, global, busy; nothing is counted unless all pass.
- **Frontend.** `RateLimitedError` carries scope and wait; `RateLimitNotice` says which limit, "Try again in about 23 minutes (around 14:32)", and links to the first recorded example. The question stays in the textarea and is also saved (`tribunal.draft.v1`, via `safeStorage`) when a limit is hit, restored on the next visit and cleared when a debate starts.
- **Known gaps:** per-IP counters are not shared between workers or restarts; the concurrent-debate count includes reruns that finish in milliseconds; there is no read-side limit, so SSE connections are unbounded.

## M6 Part 1: evaluation harness (`eval/`, outside the app)
- **Conditions from one set of runs.** Per question: run D (rounds=3, the app's normal early stop, `min_critique_rounds=1`, seed 42). A1..A3 = each debater's round-0 answer, B = majority of those three, D = judge verdict, D_vote = plurality of the last round's answers (no judge; a free diagnostic that separates debate from having a judge). C needs a judge that sees a transcript ending at round 1, so it is a second `Orchestrator(rounds=1)` run whose rounds 0-1 replay from the response cache (identical prompts) and only its judge call is new. If D stopped after round 1, C's judge prompt equals D's and C == D (no second run). Costs come from per-round `stats` snapshots of the fresh D run (cache hits report 0 ms latency); C = D's rounds 0-1 + the C judge call.
- **Known asymmetries (to be stated with the results).** D is "up to 3 rounds" (early stop on consensus; `--no-early-stop` available, not default). C and D have a judge model that A and B lack. A is a persona-prompted JSON call at temperature 0.6, one sample per question. B ties are broken by a seeded random pick and counted (`note: tie`). Per-turn repair calls are not separable, so A's calls are nominal (1).
- **Scoring.** Gold = number after the last `####`. A prediction must be a pure number by the app's own rule (`is_pure_number`, added to `consensus.py` as a public name for the existing regex, no behaviour change) and equal the gold by value. "18 dollars", "18.", "eighteen" are `non_numeric` = wrong; no answer = `missing` = wrong. No fuzzy matching. Every question is sent with "Give the final answer as a plain number with no units." appended (recorded in the manifest; disclose in results and limitations).
- **Dataset:** GSM8K test split (1319) downloaded from the original `openai/grade-school-math` GitHub JSONL with stdlib `urllib` (`python -m eval.datasets fetch`), not Hugging Face `datasets` as the PRD's FR20 suggests: no new dependency (`datasets` pulls pyarrow and pandas). The loader is a small `Dataset` interface (`load`, `score`, `prompt`, `source_sha256`) so a harder set can be added later; only GSM8K exists. Question order = seeded shuffle stored in `eval/data/gsm8k_ids_seed42.json` (commit it); the first n are used, so a pilot is a prefix of the full run.
- **Fallbacks off by default** (`--allow-fallback` enables them): every counted answer then comes from a primary model and a quota hit surfaces instead of silently switching to local gemma. Fallback use is recorded per turn and per condition either way. With fallbacks on, ledger counts are approximate (attributed to the answering provider; failed legs undercounted).
- **Resume and quota.** One JSON file per finished question, written atomically; a partial or corrupt file counts as not done. The manifest pins dataset hash, seed, prompt suffix, rounds, early-stop, fallback flag and a fingerprint of agents plus prompt files; a different config is refused unless `--force`. Only HTTP requests are counted (cache hits are free) per provider per UTC day in `ledger.json`. Defaults (unverified guesses, to be replaced by pilot measurements): openrouter 40, groq 500, gemini 200 per day; `--max-calls-per-provider` and `--max-calls-per-day` override (0 = no cap). A question starts only if its minimum calls fit; a cap that trips mid-question discards that question (the cache keeps the successful calls). Rate-limit, budget and config errors end the run with a message and exit 0; Ctrl+C exits 130; other provider errors retry the question up to 3 times, then it is listed in `skipped.json` and the run continues (retried on the next session). A model's own unparseable output is a stored wrong answer, not an abort.
- **Pause between questions:** `--sleep-between-s` defaults to 60 s, applied only after a question that sent HTTP requests. Reason: Groq's free tier is roughly 8K tokens per minute per model (unverified) and one question pushes about 6 to 8K tokens through each Groq model.
- **Where it runs:** `PYTHONPATH=backend`, backend venv Python, from the repo root. `backend/pyproject.toml` test paths now include `../eval/tests` (run plain `pytest` from `backend/`; pytest invoked with the eval path alone would not pick up `asyncio_mode`). The eval keeps its own response cache DB at `eval/cache/eval.db` (git-ignored), separate from `tribunal.db`.
- **Not in this pass:** statistics (Wilson, McNemar, paired bootstrap), the README table and limitations block (Part 2); matplotlib chart, Results page and VIS9 (decided after the pilot).

## M6 Part 2: statistics and report
- **`eval/stats.py` (standard library only):** Wilson 95% interval; exact two-sided McNemar test on the discordant counts (`math.comb`); seeded paired percentile bootstrap (10,000 resamples) of the accuracy difference. With no discordant pairs McNemar gives p = 1 and the bootstrap interval is exactly [0, 0]. **A difference is only reported when p < 0.05 and the bootstrap interval excludes 0**; otherwise the text says "no detectable difference" and never ranks by point estimate. A single non-significant result or a tiny n therefore cannot produce a winner.
- **Comparisons:** D vs B is the pre-declared primary. Exploratory (labelled so, no multiplicity correction): C vs B, D vs C, D vs D-vote, B vs each of A1..A3. A1..A3 are shown individually plus their mean accuracy (no interval on the mean); no post-hoc "best single model" row, which would be biased.
- **`eval/report.py`:** reads only `eval/results/<run>/questions/*.json` (plus manifest and `skipped.json`), never writes there, and ignores partial files, so it is safe while a pilot is running. Default prints markdown; `--write-readme` rewrites only the text between `<!-- EVAL_START -->` and `<!-- EVAL_END -->` (exactly one of each, in order, else it refuses and leaves the file alone; the file's line endings are kept, and rewriting is idempotent: no timestamps, the date range comes from the result files). No numbers are typed anywhere; the limitations block is fixed text in `report.py`.
- **Report contents:** automatic notes (very small sample when n < 30; "every condition scored 100%"; ceiling-effect note when every condition is at or above 95%, saying a difference cannot be detected on this dataset at this sample size); accuracy with all answers and primary-only (answers not via fallback) side by side with fallback counts; paired comparison table; non-numeric/missing counts and mean HTTP calls, tokens and latency; a "Debate fixed / broke" section listing question ids where B was wrong and D right (and the reverse) with gold and every condition's answer; how the debate ran (mean rounds, early stops, ties, judge failures, fallback turns, cached replays, prefix inconsistencies, skipped questions); limitations.
- **Primary-only** is computed per condition: a question is dropped from that condition's primary-only count when any turn feeding that condition used a fallback. It is not a paired analysis, so the paired tests always use all answers.
- **Limitations text** also discloses the appended "plain number with no units" line, strict matching, judge asymmetry, early stopping, one sample per question, and that costs exclude cache hits (a question re-run after an interruption can look cheaper).
- **`README.md` created** with a short stub and the two markers, because none existed; M7 writes the real README and must keep the markers.

## M6: second dataset, MATH-500 levels 4-5 (`--dataset math45`)
- **Why:** GSM8K was at the ceiling in the pilot (every condition identical), so a debate-vs-majority difference cannot show. The loader is the existing `Dataset` interface; `MATH45` is the second implementation.
- **Source and fetch:** the MATH-500 test split (`openai/prm800k`, `prm800k/math_splits/test.jsonl`, 500 rows). The plain `raw.githubusercontent.com` URL returns a git-lfs pointer, so the fetch uses `https://media.githubusercontent.com/media/openai/prm800k/main/prm800k/math_splits/test.jsonl` (stdlib `urllib`, no new dependency). A download that starts with the git-lfs pointer header, is not jsonl with the expected fields, or does not have exactly 500 rows is refused with a clear error and nothing is written. sha256 is recorded in the manifest and in the stored id list.
- **Subset:** level 4 and 5, and an `answer` that is a plain integer (optional minus sign, digits or proper thousands-comma groups; " 5", "+5", "3.5", "1,00", "x^2" are out). The count by level is printed by `sample`. Ids are `math500-<line index>`; the seeded order (seed 42) is stored as `eval/data/math45_ids_seed42.json`, so a 25-question pilot is a prefix of a 100-question run. Results go to `eval/results/math45-s42`, never mixed with `gsm8k-s42`.
- **Prompt:** the problem text exactly as the dataset has it (LaTeX included) plus "Give the final answer as a plain integer with no units." `normalize_answer` and the exact-comparison rules are unchanged; a gold with commas is compared by value. Checked: `string.Template.safe_substitute` inserts values without re-reading `$`, cache keys are JSON dumps, the report only prints ids and short answers in code spans, and the README splice uses slicing, not regex replacement. Tests with LaTeX in the question cover prompts, the cache round trip, scoring and the README splice. A model reply that writes an invalid JSON escape (for example `\(`) is an invalid answer after the repair attempt (stored as missing), not an abort.
- **Truncation check (reasoning and output length).** Level 4-5 problems need long reasoning, and `max_tokens: 1536` includes reasoning tokens for reasoning models, with Groq's gpt-oss also on `reasoning_effort: low`. Two failure shapes: an empty reply with `finish_reason=length` (already surfaced as `empty_response (finish_reason=length)`) and JSON cut off mid-way (not valid, repaired once, usually cut off again). I could not measure how often either happens without real calls, so the harness now counts it. The eval's `classify_error` treats `finish_reason=length` as the model's own failure (stored, counted wrong), not an outage: before, such a question would have been retried 3 times and then silently skipped, which would have biased the sample toward easy problems. `TurnInfo.truncated` marks an invalid turn that either reported `finish_reason=length` or whose last reply opened more braces than it closed (a heuristic; a provider that reports no stop reason cannot be told apart from malformed JSON that is also unbalanced). Per-question `facts.truncated_turns`, per-condition `truncated`, a "Cut off" column and a summary line in the report make it visible.
- **Eval-only config copy (agents.yaml is NOT changed).** `RunProfile` on the dataset: for math45 every agent's `max_tokens` is raised to at least 4096 and Groq is paced at `rpm: 2` (a config copy only; `--max-tokens N` and `--rpm provider=N` override, `0` turns each off; a limit is never lowered). Both go into the manifest (`config.profile`) and the agent fingerprint, so a changed profile is refused on resume. GSM8K has an empty profile, so its manifest and resume are exactly as before. Quota effect: the output limit does not change how many requests are sent (OpenRouter and Gemini are counted per request). It can raise the tokens Groq reserves per call against its tokens-per-minute limit (unverified how Groq counts it), hence the pacing: 2 requests/min shared by both Groq models means at least 30 s between Groq calls, so about 3 to 8 Groq calls per question take 1.5 to 4 minutes of pacing. A truncated first reply also costs a repair call, so the estimate's upper bound is multiplied by 1.3 (a guess to be replaced by measurements).
- **Pause between questions:** default by dataset, 60 s for gsm8k (unchanged), 120 s for math45, because a MATH question is expected to push about twice the tokens through each Groq model; `--sleep-between-s` overrides. All of it (4096, rpm 2, 120 s, 1.3x) is a guess until the n=3 run shows real token use and 429s.
- **Report:** names the dataset ("MATH-500 test split, levels 4-5, integer answers only"), lists the eval-only settings, and the limitations block is now generated per dataset: for MATH it says the data is very likely in the models' training data (contamination), the sample is a small subset, the integer-only filter makes it easier than the full benchmark (scores not comparable to published MATH results), and, when an output limit was raised, how cut-off answers are counted. `--write-readme` still replaces whatever sits between the two markers, so choose which run to publish.

## M6: LaTeX escapes in model JSON, and per-turn diagnosis fields
- **Diagnosis (math45, n=3, from the response cache).** All 7 unusable Gemini replies behind the "no valid answer" turns (Q188 rounds 0 and 1, Q145 round 1, Q371 round 0 repair) were complete JSON that failed only on LaTeX written with single backslashes inside a string (`\le`, `\in`, `\lfloor`, `\sqrt`: "Invalid \escape"). Both the first reply and the repair reply failed the same way, so every such turn cost two calls and counted wrong. Not a token-limit or hidden-reasoning problem. Q371 Gemini round 0 also had one genuinely cut-off first reply (4092 of 4096 output tokens, one brace unclosed); its repair reply was complete and parses with the fix. The Q371 Nemotron round-0 turn (0/0 tokens) was an empty reply, recorded as `truncated` only through the `finish_reason=length` error marker; failed calls are not cached, so its text cannot be inspected.
- **Fix: strict parse first, escape only on failure.** `extract_json` runs the old logic unchanged; only if it finds no object does it retry once on the same candidates after doubling every backslash that does not begin a legal JSON escape (`\` pairs are consumed together, `\u` counts only with four hex digits). Anything that parsed before returns the identical object (checked against all 86 cached replies that parse strictly: 0 changed). It lives in the shared parser, so it works the same for every provider and also fixes the app, where a math answer in LaTeX would have cost a repair call or an invalid turn. Known limit: a mix of legal LaTeX-looking escapes (`\frac`, `\text`, `\neq`, `\beta` read as form feed, tab, newline, backspace) and an illegal one still parses with those characters altered inside the reasoning text, as before. Only the final answer is scored and it is a plain integer, so scoring is not affected. Truncated or otherwise broken JSON still fails.
- **Stored per turn in eval result files:** `finish_reason` (last call; `null` for cached replays and providers that report none), `raw_tail` (last 300 characters of the last reply), `repair_used` (a second call was needed) and `error` (provider error text, 300 characters). `CompletionResult` gained `finish_reason`, set by the OpenAI-compatible provider; the cache does not store it. Old result files lack these keys and stay valid. No change to token limits, reasoning settings or `agents.yaml`; the agent fingerprint is unchanged, so existing runs still resume.

## MMLU-Pro eval, Stage 1 (loader, selection, extractor, hook, report; no run yet)
- **Question asked.** One pre-declared comparison: D (judge after up to 3 rounds) vs B (plurality of the three round-0 answers), paired, on MMLU-Pro with a weaker free-tier cloud panel. A1-A3 are shown descriptively with no tests. C and D-vote are not run for this dataset (`Dataset.runs_c = False`); other datasets are unchanged.
- **Not compute-matched.** D uses about 7 to 13 requests per question against 3 for B. Weaker free-tier panel only. The judge (gpt-oss-20b) is the same model as debater 2. MMLU-Pro may be in training data. At n = 60 only differences of roughly 15 points are detectable; "no detectable difference" is not evidence of no difference.
- **Data.** `python -m eval.mmlupro fetch` pages the HF datasets-server rows API (100 rows per request), validates every row (exactly 12,032 rows, 2-10 options, answer inside its options, unique ids, no truncated cells), refuses a short or malformed download and writes nothing. The pin is the sha256 of the normalised JSONL (key-sorted, compact, one row per line); `eval/data/mmlupro_manifest.json` is committed, the raw file is gitignored, and a later download that hashes differently is refused. These API details (row count, field names, option range) are from memory and unverified until the first real fetch.
- **Selections.** 5 categories (chemistry, physics, engineering, law, economics) x 12. The holdout (seed 2026) is drawn first; a screen (seed 42, then new seeds) is drawn from the pool minus the holdout and every other screen, so a rescreen is disjoint by construction. Existing selection files are never overwritten. Disjointness is asserted when drawing and whenever either dataset loads, and tested.
- **Letter extraction.** Strip, drop one trailing period and one pair of parentheses, uppercase, accept only A-J; fallback "answer is X" (the letter must end the text) on `final_answer` only. An optional `answer_normalizer` on `Orchestrator` (default None = unchanged, so the app and old runs are untouched) applies it to every debater and judge answer right after parsing, so consensus, early stop, peer prompts and the judge transcript all see the same letter; the model's text is kept as `final_answer_raw` where it differed. A reply that is not a letter scores `invalid` and does not vote in B.
- **B tie-break made order-independent.** `majority()` seeded its tie-break per question but chose from leaders listed in turn-completion order, so a live run and a cached replay could differ. Leaders are now sorted by answer key first. Only tied B/D-vote outcomes can change; stored results are not rewritten.
- **Run shape.** `EvalSettings.include_c`: no C run, C and D-vote not derived, the estimate counts exactly one judge call, report rows/comparisons/limitations follow the conditions present. Added to the manifest only when False, so existing runs still resume. The report adds the per-model letter distribution, accuracy by category and the B tie rate.
- **Not done yet (later stages):** the eval-only panel config, `eval/screen.py` (both Gemma and gpt-oss-20b), the holdout guard, the prompt/extractor hash pin, commits. Profile numbers for MMLU-Pro (2048 output tokens, Groq 4 requests/min, 60 s pause, 1.3x repair allowance) are guesses.
- **Per-question answer range (added before any real run).** The suffix was a fixed "A to J" and the extractor accepted A-J for every question, so a 4-option question would have accepted an "H" as an answer. Now the line sent is "Answer with only the letter (A to {last}) of the correct option." with the question's own last letter (A to D for 4 options, A to J for 10), and the extractor, the plurality vote and the scorer accept only letters within that question's options (`extract_letter(text, n_options)`). `Dataset.normalize_answer`/`is_valid_answer` take the question; the orchestrator hook is bound per question.
